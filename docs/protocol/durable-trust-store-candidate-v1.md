# Durable NetworkRoot trust store candidate v1

Status: implementation candidate, not frozen protocol and not production acceptance. Scope is only persistence of root-signed issuer authorization candidates. The store is not a general trust framework and does not implement `StatusSnapshot`, revocation application, freshness latches, TLS certificates, Genesis/root rotation, or runtime startup.

## Inputs and API

`boreas_pki::trust_store::DurableTrustStore::open(path, net_id, pin, trusted_owner_uid)` is available only with `openssl-backend`; this initial implementation supports Linux only and returns `Unsupported` on macOS/Windows/other targets. The open path cryptographically re-verifies stored signed history at the signed not-before boundary without granting current-use validity; `import` and `issuer` require explicit caller trusted time. `pin` is the separately provisioned `root_authorization::NetworkRootPin`; no caller bool, self-asserted verified metadata, nor cached `IssuerRecord` is accepted. `trusted_now_us` and `trusted_owner_uid` must come from trusted deployment inputs (the latter is an independently established expected local UID; this API does not discover the process effective UID). Open rejects another network or pin fingerprint. The independently provisioned pin remains external and must be obtained over a channel independent from ReleaseRoot/software distribution.

`import(raw_candidate, ed25519_signature, mldsa_signature, pin, trusted_now_us)` invokes `verify_raw` over the exact canonical bytes, requiring both real signatures and validity at the supplied time. It commits before returning `Added`. Same issuer key ID + generation + exact raw candidate is idempotent and does not renew validity. Lower generation is rejected. Same generation with different valid raw candidate stores both exact evidence items in a durable quarantine and rejects; the slot remains quarantined across restart. `issuer(key_id, pin, trusted_now_us)` re-verifies the stored raw candidate and both signatures against the current external pin and returns a private-field `VerifiedIssuerAuthorization` only if it is valid at this call's trusted time. The caller can convert it to the existing management `IssuerRecord`; it must still scope that record to the same network/context.

## Disk format candidate

All integers are unsigned big-endian. `BRTS\0\0\0\x01 || net_id[16] || root_pin_fingerprint[32] || accepted_count:u16 || accepted_entries || conflict_count:u16 || conflict_entries`.

A normal entry is `issuer_key_id_len:u16 || issuer_key_id || auth_blob`, where `auth_blob` is `raw_candidate_len:u16 || raw_candidate || ed_sig_len:u16 || ed_sig || mldsa_sig_len:u16 || mldsa_sig`. A conflict entry is `issuer_key_id_len:u16 || issuer_key_id || generation:u64 || first_auth_blob || second_auth_blob`; the key id occurs once per slot. Candidate bytes are capped by `root_authorization::MAX_CANDIDATE_BYTES`; key id <=64, Ed25519 signature <=64, ML-DSA signature <=4627; total state <=4 MiB, and combined accepted/quarantined issuer slots <=256. Unknown version, malformed/trailing bytes, duplicate keys, count/length overflow, oversized files, wrong network/pin fingerprint, or any bad signature fail closed. Exact root signature bytes are retained; no re-encoding substitutes are written.

The stored fingerprint is SHA-256 over a fixed domain, length-prefixed net ID, algorithm tags, and length-prefixed Ed25519/ML-DSA SPKI DER. It identifies the externally provisioned public pin for reporting/change detection; it is not a proof of provenance or independent trust by itself.

## Storage and durability

On Linux only (other targets return `Unsupported`) the storage directory path is absolute and each parent component is checked as a non-symlink directory; the canonical final directory must be owned by `trusted_owner_uid` with no group/other permissions; the final file and persistent sidecar lock must be single-link regular files mode 0600 owned by that UID. Opens use `O_NOFOLLOW`; staging uses `O_CREAT|O_EXCL|O_NOFOLLOW` in the same directory. A persistent sidecar advisory exclusive lock is held for the store lifetime and is never unlinked. Commit order is: encode and bound the full next image; exclusive same-filesystem staging create; write all; `sync_all` staging file; atomic rename over state; `sync_all` parent directory. If a crash leaves the fixed `.staging` path behind, the next open refuses it rather than deleting or adopting unauthenticated staging bytes; operator recovery must preserve/inspect evidence and remove only the verified stale file while holding exclusive store lock before retrying. Automatic crash recovery from a prepared staging image is not implemented. Failed operation poisons the instance and denies further business use; before rename the previous state remains; after rename but failed directory sync outcome is uncertain, so use must stop and reopen/recover before any action. Windows returns `Unsupported`; it does not claim durability.

Restart validates the bounded image, root fingerprint and every retained exact raw candidate/signature pair against the supplied independent pin. Verification uses the candidate's signed not-before boundary to authenticate already persisted evidence independent of the current time; it does not alter signed validity. Any record exported for use is re-verified against the caller's current `trusted_now_us`, so restart never resets authorization expiry.

## Boundaries and open issues

The final storage directory is private and must match caller-designated `trusted_owner_uid`; its ancestors may be non-writable by untrusted users, with root-owned sticky directories such as `/tmp` allowed. This module does not authenticate that UID or discover the process effective UID. Deployments must provision it independently. A local filesystem administrator able to rewrite the whole store can still restore an older internally valid image. Without a hardware-backed counter, independent remote watermark, or separately protected append-only authority, this module cannot magically detect whole-disk rollback. It also does not check status freshness/revocation or produce a `FreshStatus` capability: complete `StatusSnapshot` verification, clock persistence/rollback logic and state refresh are explicitly out of scope.

Per-network file separation and exact `net_id`/pin fingerprint binding prevent accidental cross-network reuse; deployments must additionally isolate storage paths and must never supply ReleaseRoot as the NetworkRoot pin. This is a candidate local persistence contract, not an external audit or production-ready declaration.
