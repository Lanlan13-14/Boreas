# Platform support and CI evidence

## Current status

This repository is a **development foundation**, not a production VPN. The CLI implements policy/parser-facing `doctor`, `self-check`, and `help` behavior; there is no integrated production daemon or production resource lifecycle. The workspace does contain library-level socket/TCP-TLS-WebSocket runtime seams, optional OpenSSL-backed pq768 TLS/PKI paths, enrollment and dual-signature verification slices, DNS TCP state-machine code, and Linux TUN/Wintun/utun device adapters. These are real code slices with selected upstream CI evidence, not a daemon-connected VPN path, complete platform routing/install integration, or an accepted production update path. A successful platform build proves only the scoped build/tests on that runner; it does **not** demonstrate usable VPN functionality, security, performance, or readiness for release.

All compilation and tests are run in GitHub Actions. Do not run Cargo, Rust, Python verification, or platform tests locally. Workflow artifacts are named and described as development-only; this workflow does not create GitHub Releases, publish packages, push images, sign artifacts, or treat tags as production releases. Do not create a production release/tag until all applicable Phase 0–5 evidence gates and external review in the master plan have passed. CI has no access to offline release signing keys. Real production manifests require the project’s separately controlled offline dual-signing process; CI credentials must never substitute for it.

## Platform-specific implementation gaps

| Area | Linux | Windows | macOS | Required before claiming production support |
|---|---|---|---|---|
| TUN/L3 device | `boreas-tun` has Linux device/PacketIo library code; upstream run [43676629745](https://github.com/Lanlan13-14/Boreas/actions/runs/43676629745) passed scoped real-device tests and anti-skip guard, not integrated VPN forwarding | Wintun adapter exists; upstream run [43677035773](https://github.com/Lanlan13-14/Boreas/actions/runs/43677035773) passed scoped real packet-I/O job | utun adapter exists; same upstream run passed real packet-I/O jobs on x86_64 and arm64 | Integrate each adapter with daemon forwarding/routing, lifecycle, privilege and recovery; run full per-OS packet-path acceptance |
| Routing and firewall | No production route/rule manager or real host coexistence evidence | Windows route and firewall API behavior remains unintegrated | macOS route and packet-filter integration remains unintegrated | Add non-destructive apply/rollback, management-route protection, privilege, failure and reboot recovery tests per OS |
| Isolation/sandbox | Linux seccomp/ABI slices are not accepted production evidence | Linux seccomp is not a Windows sandbox; choose and audit Windows-native process isolation/mitigations | Linux seccomp is not a macOS sandbox; evaluate and audit an appropriate macOS-native sandbox | Separate threat models, implementation, positive/negative tests and audit evidence for each OS; never label the Linux seccomp result cross-platform |
| Networking and crypto | Runtime/library includes TCP/TLS/WebSocket seams and optional OpenSSL pq768 backend; upstream [43677030789](https://github.com/Lanlan13-14/Boreas/actions/runs/43677030789) passed scoped backend tests, not G-CRYPTO or production daemon integration | Platform build does not establish backend equivalence; no integrated daemon TLS path | Platform build does not establish backend equivalence; no integrated daemon TLS path | Complete Phase 0 backend, independent interoperability and fail-closed tests on each supported platform/backend configuration |
| Operations and upgrades | Supervisor/journal library slices exist; no production service integration or accepted recovery evidence | No Windows service integration or accepted upgrade/recovery | No launchd/service integration or accepted upgrade/recovery | OS-specific packaging, least-privilege operations, verified upgrade/rollback, crash and recovery tests |

`Wintun`, `utun`, route APIs, packet-filter/firewall APIs, service managers, and sandbox primitives have different lifecycle and security properties. The cited Wintun/utun CI is real device packet-I/O evidence for the adapters, but does not integrate them with a production daemon, routes, firewall or service lifecycle. A platform-neutral Rust API or Linux-only test is not proof that these facilities work on Windows or macOS. Do not claim production support for an OS capability until that platform has the complete implementation and evidence.

## Release gate

Production release is **blocked** until the applicable master-plan Phase 0–5 gates, security review, attack/fault testing, platform-specific TUN/routing/sandbox and upgrade evidence, reproducible build/supply-chain evidence, and offline dual-signature verification have been completed and reviewed. CI build/test success and development artifact upload are necessary engineering feedback only; they do not pass those gates. Keep development artifacts clearly labeled, run-scoped, and unsigned by production keys. Do not trigger production publication from a version tag or workflow-dispatch input in this workflow.
