# Direct Linux Edge/Core multi-active E2E candidate

`boreas daemon serve` and `boreas daemon connect` accept the explicit
`--e2e-active-lanes 2|3|4` flag on Linux/OpenSSL builds. Set the same count
and `--mtu` on both daemons. Retain all normal material, durable status,
network-policy and anti-rollback arguments. On Edge, use explicit `--connect`
with a literal IP:port and normal outer TLS naming/trust (`--tls-name` and
`--ws-host` where needed). Omitting the flag preserves the legacy
single-active/optional-standby behavior and its E2E wire format. A mismatch
fails; there is no downgrade, alternate ingress retry or plaintext fallback.

The fixed cohort has one provisioned or newly created real Linux TUN queue
per endpoint and one independently authenticated TCP/WSS + pq768 hop + pq768
E2E socket per lane. Socket admission is ordered, bounded by a common 45 s
startup deadline, with at most one in-progress handshake and at most four
socket owners in the process. Core accepts only this cohort; neither endpoint
forwards until all required lanes are locally authenticated and bound to the
same verified NodeIdentity pair, signed network context and permanent VIPs.
A new daemon invocation is required after a terminal loss; the listener does
not admit another cohort in the same process.

After the separately authenticated BE2E v2 exchange on each circuit, this
candidate adds a 26-byte TLS application message (`BCOH`, version byte `1`,
kind byte `0` for Offer / `1` for Ack, zero-based ordinal, count, two-byte
big-endian runtime MTU, and a fresh 16-byte cohort nonce generated by Edge).
Core checks all fields and the nonce from the first admitted lane before
acknowledging subsequent lanes. Edge requires the exact Ack. The final lane
then carries a second exchange using the same fields (kind `2` for Commit /
`3` for CommitAck), after the participating endpoint has locally authenticated
all preceding lanes. No bytes of these records pass to TUN. This is a
candidate wire extension, not a registry
assignment or compatibility promise. Peer authentication and the existing
signed status/identity gates remain mandatory; the nonce confers no trust.

One dispatcher owns all host reads and writes. Each socket worker owns its
full TLS stack and the usual authenticated `PacketPath`. A per-pair
`CircuitPool` round-robins new SYN tuples across established lanes, learns
peer SYNs on their observed lane, and keeps both directions on that lane.
The per-lane FIFO queues hold at most 64 MTU-bounded packets per direction.
A full queue drops at that lane boundary; no packet is migrated or replayed.
A stalled frame operation has a 30 s absolute dispatcher-observed limit.
The policy/status cutoffs and identity-revocation watchdog apply jointly;
any terminal protocol, transport, TUN or trust failure cancels all sockets
through owned descriptors and joins the workers. Clean peer close requires
TLS close on all lanes; a planned `--max-seconds` stop attempts bounded close.
`ctl status` reports the active connection count and `multi_active_lanes`
(one-based lane ordinals and sent/TUN-delivered packet totals).

Scope: direct permanent-VIP IPv4/TCP only. No ICMP, UDP (including private
DNS), IPv6, IP fragments, TUN GSO, virtual TUN, `--max-packets`, mesh/CDN
verification, dynamic lane replacement or standby/failover. The 4,096 tuple
slots are not automatically retired or evicted in this baseline; long-lived
instances reaching the limit stop admitting new tuples instead of moving
existing ones. Simultaneous TCP opens for the same tuple on different lanes
fail closed. Polling, buffering and lack of retirement have not been tuned
for deployment or performance.

## Privileged verification on the target Linux runner

With a candidate built with OpenSSL 3.6+ and `openssl-inner-tls`, run the
following from the repository root under the existing namespace smoke
prerequisites (`/dev/net/tun`, `ip`, `ss` with socket-destroy support, Python,
root network namespace privileges and the signed fixture tooling):

```bash
BOREAS_NETNS_E2E_ACTIVE_LANES=4 bash tools/release/netns_daemon_smoke.sh /path/to/boreas
```

Repeat with `2` and `3`; also run the existing smoke without the flag to cover
unchanged defaults. The opt-in run provisions the usual trusted materials,
checks distinct established underlay TCP sockets, verifies integrity for four
application TCP flows in each direction, requires TX and RX progress on every
admitted lane, then destroys one selected transport inside the disposable
namespace and requires both daemons to halt nonzero without a promotion.
No performance or release gate is implied by a passing fixture. The fixture
was authored but not executed in the implementation container.
