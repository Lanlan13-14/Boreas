# Data-plane state primitives: limits and integration boundary

Historical primitive-design note: the sections below describe isolated state types, not the complete current product. The Linux point-to-point daemon now has a real WSS/hop/E2E TLS and TUN path; that does not complete these primitives' topology-wide integration or the production resource audit. All plan gates remain open; see [the v1.11 master plan](../plans/BOREAS-MASTER-PLAN-v1.11.0.md) §11 and [the implementation gate ledger](implementation-status.md).

## Short daemon resource observations (candidate, pending Actions)

The netns smoke samples the recorded Core/Edge exec PIDs during its concurrent bidirectional transfer, approximately every 100 ms, bounded to 500 samples or 45 seconds. Before accepting a process, its executable device/inode must match the tested binary; every sample must retain the same process starttime and executable identity. Wrapper processes, substituted PIDs, missing samples, unknown clock-tick/page units and insufficient windows yield `unmeasured`, never fabricated values. Installed OpenWrt rootfs copies have different inodes and currently report `unmeasured`.

CPU seconds are the process thread group's user+system tick delta divided by the kernel-reported `SC_CLK_TCK`; CPU percentage is relative to one CPU over the observed window. RSS is the maximum sampled resident-page count times `SC_PAGE_SIZE`, not a lifetime high-water mark. Sampling excludes handshake/startup, child CPU, kernel socket memory, PSS and total cgroup usage; 100 ms sampling can miss short peaks and perturbs the workload. There is no arbitrary CPU/RSS pass threshold; unavailable observations do not turn a functional smoke green or red. Original functional, security and performance gates remain mandatory.

This short two-node observation does **not** satisfy the full plan's `G-RESOURCE`: 195/291-connection load, admission attacks, stopped readers, TLS/HTTP2 costs, 30-minute endurance, RSS/PSS/cgroup/sockstat/credit/queue accounting and unexplained growth analysis remain open. No CPU/RSS improvement or budget acceptance is claimed until actual exact-commit evidence is reviewed. Syntax/build/test execution remains GitHub Actions-only.

## Underlay TCP kernel telemetry (`ss -tin`)

The same netns smoke brackets its concurrent bidirectional transfer with two namespace-scoped snapshots: one immediately before the first probe worker starts and one after all four workers are reaped. Inside each disposable Core/Edge namespace it runs `ss -tin` and keeps only sockets of the fixed underlay pair (Core `192.0.2.1:8443`; Edge `192.0.2.2:<ephemeral>` → `192.0.2.1:8443`), together with that socket's raw `TCP_INFO` continuation line: rtt/rttvar, retransmits, cwnd, bytes_acked/bytes_received, delivery rate and the remaining fields. The output is emitted next to the daemon resource sample. Each capture is bounded to five seconds; absent `ss` or `timeout` yields unavailable evidence. The before/after capture overhead lies inside the resource sampling window, so CPU-window percentages include this timing overhead.

This is collection only, scoped to the disposable namespaces and read-only over their own `/proc`: no host sysctl, qdisc, route or interface change, and no change to transfer, ping, deadline, byte-count, key-material or security state. No threshold is asserted and nothing is retried; a partial, failed or unmatched capture is reported as `unmeasured`/`no-matching-socket` and never turns a failed functional, security or performance assertion green.

**Field scope:** these numbers describe the underlay TCP connection that carries the outer TLS transport. They are **not** cross-layer latency attribution: WSS, hop/`RelayCircuit` forwarding, overlay TUN encapsulation and the pq768 inner E2E mTLS all sit outside the measured socket, so an `rtt` sample here is neither an end-to-end nor an application latency and cannot be decomposed across those layers. This telemetry also does not satisfy `G-RESOURCE`, `G-PERF`, `G-DATA` or `G-E2E`.

## Startup/handshake stage timing (netns smoke)

The same smoke records harness-observed startup boundaries with one monotonic `/proc/uptime` timestamp per phase, read through a shell builtin so no timer process is spawned on each poll and the existing loops keep their exact poll counts, intervals and daemon `--max-seconds` bounds. Values are integer milliseconds derived by truncating the uptime fraction to three digits; `/proc/uptime` commonly advances in 10 ms steps, so the timings are monotonically ordered but not a CPU-time measurement. The stages are: Core launch → first observed `btun0`; Edge launch → first observed `btun0`; Edge launch → connected-poll resolution (success or failure); observed Edge TUN → connected-poll resolution; and the connected-wait duration itself, i.e. the fixed 100 × 50 ms (≈5 s) window. At the Core TUN, Edge TUN, connected-wait start and connected-resolution boundaries it also records, per node, whether `boreas ctl status` answered and whether that answer contained `"daemon_connected":true` (`available-connected`, `available-not-connected`, `unavailable:ctl-exit-N`). Only that classification is emitted; raw status output and error text are discarded, so no path list or key material is dumped.

These durations are observation latency between a launch and a harness boundary, including process start, `ip netns exec`/`unshare`/mount setup, TUN creation, config, the diagnostic `ctl` probes and 50 ms poll granularity. They are not CPU time, crypto service time or queueing delay. A connected-loop expiry means only that this harness observed no `"daemon_connected":true` within its fixed window: that window is a harness wait bound, not total handshake/crypto/CPU time, and an unconnected outcome inside it neither proves a harness error nor attributes the delay to crypto, CPU or the transport. Edge TUN → connected is only an upper bound on the post-TUN handshake window as seen by the harness.

Collection only: the poll count, 50 ms interval and daemon deadlines are unchanged, and no retry, extra wait or threshold is added. The one-shot per-node `ctl` probes are themselves observation overhead: the two pre-loop probes run before the connected-wait clock starts, so that duration excludes them, while Edge launch → connected and Edge TUN → connected include their process-spawn latency; the post-loop probes run after its end timestamp. The harness therefore does not claim the timings are identical to a probe-free run or that the effective observation window is unaffected. An unreadable clock becomes `unmeasured`, ctl probes gate nothing, and no timing result can pass or fail an assertion. The timings are instrumentation, not root-cause evidence for any one-way delay or packet-loss observation, and they lie outside the resource-sampling window described above.

## Resource admission (`resource.rs`)

- `Admission` is a cloneable global ledger with mutex-protected counters and RAII guards.
- `reserve_handshake()` reserves a single global unauthenticated handshake credit. It accepts no claimed identity/key ID, so an unauthenticated peer cannot debit another peer's quota.
- `HandshakeCredit::authenticate()` converts the global reservation to global and per-verified-peer authenticated connection counts. There is no production `AuthenticatedPeer` constructor yet; tests use a private `cfg(test)` constructor. A future trusted identity-verification integration must be the only production source, and no public method currently manufactures it from network data.
- `ByteCredit` holds the global byte charge for the full lifetime of an owned queue/circuit reservation and releases on drop. Relay payloads move out as `PreopenPayload`, which owns both bytes and credit; the charge remains held while the payload remains live, even after queue consumption or reset.
- The mutex serializes admission decisions; this is a first correctness primitive, not proof of lock latency or global process memory enforcement. Select limits from measured budgets and include allocator/transport overhead separately.

## Scheduler (`scheduler.rs`)

`DrrScheduler` is FIFO within each flow, uses byte deficits/quantum across flows, rejects zero-byte items to prevent metadata-only queue growth, and applies fixed packet/byte/flow and queue-age bounds. It is deliberately **not an RFC 8290 FQ-CoDel implementation**: no hash classifier, CoDel control law, ECN, or socket integration is provided. It rejects zero-byte entries to prevent metadata-only queue growth and refuses zero quantum/zero capacity configuration. It does not silently discard ciphertext. `DequeueError::QueueAgeExceeded { flow_id }` identifies the flow to reset. `DequeueResult::PendingCredit` is distinct from `Empty` and means backlog remains but needs another bounded dequeue pass; callers must reschedule without waiting for a new arrival. Once an age failure occurs, the caller must reset the logical flow/circuit and explicitly purge it; purged payloads are returned for caller-directed disposal and are never reported as delivered. The caller should preserve ordering for a given flow and must not retransmit stale ciphertext under a new session.

## Relay circuit lifecycle (`relay.rs`)

- `CircuitId` is a caller-provided 128-bit value. The production caller must generate it with an OS CSPRNG; this module does not generate IDs or authenticate them.
- Circuit endpoints bind `NodeID` plus `identity_generation`; equal NodeIDs are rejected even if generations differ. Circuit pairs are canonicalized regardless of direction; default is **one** circuit per pair, and configuration accepts only `1..=4`. The table also has a global hard circuit limit. Integrators must still ensure endpoint claims came from verified objects.
- Hop budget must be in `1..=8`; forwarding decrements it and exhaustion resets/fails closed.
- Each direction has an independent `u64` byte offset. Segments are accepted only at the exact next offset and only for the bound source, destination and generations. This records metadata continuity; it does not authenticate ciphertext or validate a TLS record.
- Before establishment, queue payload is limited to 64 KiB per circuit **and across all circuits of one canonical peer pair**, at most 128 queued entries per pair, globally charged by `ByteCredit`, and expires two seconds after opening. Empty payloads are rejected to prevent unbounded metadata-only entries. Establishment after the two-second deadline fails closed. Queue payload is not application delivery.
- Circuit lifecycle is capped at 900 seconds. The state method `mark_established` means only that the table transitioned state; it is **not** evidence of E2E TLS. `consume_preopen` and `accept_segment` require an opaque `VerifiedE2eSession` capability with no public constructor. Only a future TLS integration in the trusted crate boundary may produce it; until then production traffic cannot enter or leave as active E2E.
- A real implementation still needs pair accounting tied to authenticated peer sessions, simultaneous-open tie-breaking, reset propagation, replay/offset failure policy, TLS/E2E identity binding, cancellation/race behavior, and persistence/restart semantics as applicable.

## Test and release boundary

Unit tests use injected `Instant` values for deterministic age/expiry transitions. No local build or tests are run by this delegated task; CI must format, compile, lint and test the workspace. Passing these unit tests would establish only these isolated state invariants, not the plan's `G-RESOURCE`, `G-DATA`, `G-PERF`, `G-E2E` or production release gates. Do not claim successful TLS/E2E, bounded total process RSS, RFC 8290 compliance, static TLS builds, or completed Phase 0.
