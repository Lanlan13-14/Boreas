# Phase 0 TLS 双实现后端调研（Rust 集成路线与独立互操作候选）

**观察时间：2026-11-15（Asia/Shanghai）** **范围：BOREAS Master Plan v1.11.0 §4 密码架构、Phase 0 `G-CRYPTO` 门禁。** 本文每条 `[事实]` 后均跟一手链接（GitHub 固定 tag 源码 / GitLab tag 源码 / crates.io / docs.rs / IETF datatracker / 官方文档站）；未取得一手证据的条目标 `[待证]`，不得当作支持证据。本文是只读调研，不运行握手、不修改代码、不承诺 `G-CRYPTO` 已通过。

## 推荐结论速读

- `[建议]` **主实现继续走 OpenSSL 3.6.1 + Rust `openssl 0.10.82`/`openssl-sys 0.9.118`**：该 Rust 绑定已逐个暴露 groups、sigalgs、TLS 1.3 AEAD、证书/私钥加载、关闭 tickets/session cache 与 0-RTT 控制点（见 §1 API 清单）。静态发行**不要用 `vendored`**（它锁定 OpenSSL 3.2.0，与已取证的 3.6.1 tag 不一致，见 §1.4），应自建 `no-shared` OpenSSL 3.6.1 后用 `OPENSSL_DIR` + `OPENSSL_STATIC=1` 指向 musl target 构建；其正确性仍需 x86_64/aarch64 本机握手实证 `[待证]`。

### 1.3 主要缺口与钉死项（不是 API 没有，就是策略更严）

1. **协商组读数缺口 `[事实]`**：在 `openssl 0.10.82` 的 `ssl/mod.rs` 全文检索 `group`（不区分大小写）只命中 `set_groups_list` 等 setter，未见 `negotiated_group`/`SSL_get_negotiated_group` 安全封装；`openssl-sys` handwritten [`ssl.rs` 515-516](https://github.com/rust-openssl/rust-openssl/blob/openssl-v0.10.82/openssl-sys/src/handwritten/ssl.rs#L515) 仅导出 `SSL_ctrl`/`SSL_CTX_ctrl`，`openssl-sys/src/ssl.rs` 内只 grep 到 groups/sigalgs setter 包装（443-480），未 grep 到 `SSL_get_negotiated_group` 外部声明。后端若要无硬编码假设地读取协商组，须经 `openssl-sys` FFI（必要时 `SSL_ctrl(SSL_CTRL_GET_NEGOTIATED_GROUP)`）或等上游加封装；**以 configured list 推断 negotiated 属于禁止事项**，既有评估与脚本纪律均要求“应实际记录 group 0x11EC，不允许从 config 假设推导。他线 `backend.rs` 当前已在隔离模块内破例：其 `configure_strict_context` 把“仅提供一組，握手成功即必然名为 X25519MLKEM768”作为受限上下文的交集论证（注释在 set_groups_list 前），且 `negotiated_parameters` 将 `peer_signature` 亦由对端证书为 ML-DSA-65 的事实回填为 `MlDsa65`、`zero_rtt: false` 以“未暴露 early-data API”常量收录。这三点在密码层面都有合理面，但作为 `validate_negotiated` 的实测证据，评审应要求：要么采 FFI 实读 negotiated group 与 peer sigalg 并落日志，要么在 ADR 中正式把交集论证收为有据推断并用独立实现互操作交叉印证——不得默默将三者过账为已测事实。另注意 `boreas-crypto` 库本体曾 `#![forbid(unsafe_code)]`（他线改后已取消并隔离至 `backend` 模块、其 `session_reused` 已实际调 `openssl_sys::SSL_session_reused`）；该 FFI 的落位仍属实现 ADR 事项，本文不替实现者拍板。
2. **`signature_algorithms_cert` 未暴露 `[事实]`**：`set_sigalgs_list` 对应 `SSL_CTX_set1_sigalgs_list`（1792-1800 行），不能单独约束证书本身的链签名算法（即对端叶子/链可否用 ECDSA 等签名）。主计划要求全链 ML-DSA 时，后端必须在 verify 回调中逐张查 `X509::signature_algorithm()` 与 `public_key()` 的算法标识补足，不能只靠 `set_sigalgs_list("mldsa65")`。
3. **无独立的 “禁止 0-RTT” 与 “peer sigalg 枚举” 安全封装**。0-RTT 靠 `set_max_early_data(0)`（§1.2）；peer 的 CertificateVerify 签名方案也未见与 negotiated group 同等的直接 getter——应用层需要以对端叶子证书算法 + `signature_algorithm()` + 完整握手日志三者交叉，缺一不算读到 `0x0905`。
4. **security level 容易误伤**：`set_security_level` 同样暴露（1830 行）；OpenSSL 默认 level 1 与 ML-DSA security bits 的关系需显式评审后钉死，后端**不得无声写 0**——写几应在后端 ADR 中记理由并留正负测。


### 1.4 静态链接 OpenSSL 的正确做法：`vendored` 陷阱与自建注入

- `[事实]` **当前钉版的 `vendored` 不是 3.6.x，而锁定 OpenSSL 3.2.0**：`openssl-sys 0.9.118` 声明 feature `vendored = ['openssl-src']` 且依赖 `openssl-src = { version = "300.2.0", features = ["legacy"] }`（[openssl-sys/Cargo.toml 19、33 行](https://github.com/rust-openssl/rust-openssl/blob/openssl-v0.10.82/openssl-sys/Cargo.toml#L19)）；`openssl` crate 的 `vendored = ['ffi/vendored']` 只是转发（[openssl/Cargo.toml 21 行](https://github.com/rust-openssl/rust-openssl/blob/openssl-v0.10.82/openssl/Cargo.toml#L21)）。`openssl-src` 的版本规则为 `X.Y.Z+B`、主版本 `300` 表示 OpenSSL 3.Y.Z 兼容系列（[openssl-src README](https://github.com/alexcrichton/openssl-src-rs/blob/main/README.md)），其 tag 列表含 `300.2.0+3.2.0`，即 crate 300.2.0 内置 OpenSSL 3.2.0（[openssl-src tags](https://github.com/alexcrichton/openssl-src-rs/tags)）。**因此不得用当前 vendored 继承 OpenSSL 3.6.1 的证据**（2026-11-14 评估系于 3.6.1 固定 tag 源码；本文未对 3.2.0 自身能力另行取证）；且 feature 名 `"legacy"` 表示同时构建 legacy provider，与 PoC “仅激活内建 default provider”的最小信任面不一致。结论：`openssl-backend` 启用时**不得加 `vendored`**，`Cargo.toml` 当前 feature 定义恰好避开了这一坑（只含 `dep:openssl`、`dep:openssl-sys`）。
- `[事实]` **非 vendored 的发现逻辑**在 `openssl-sys/build/`：构建入口若启用 `vendored` 则先走 `find_vendored::get_openssl`（仅 `OPENSSL_NO_VENDOR` 非 `0` 可关闭），否则走 `find_normal::get_openssl`（[build/main.rs 48-58](https://github.com/rust-openssl/rust-openssl/blob/openssl-v0.10.82/openssl-sys/build/main.rs#L48)）；`find_normal.rs` 优先读 `OPENSSL_LIB_DIR` + `OPENSSL_INCLUDE_DIR`，缺一则读 `OPENSSL_DIR`（其下探测 `lib64`/`lib` 与 `include`），最后才 pkg-config/vcpkg（[find_normal.rs 8-28](https://github.com/rust-openssl/rust-openssl/blob/openssl-v0.10.82/openssl-sys/build/find_normal.rs#L8)）；`determine_mode` 以 `OPENSSL_STATIC` 环境变量为准，非 `0` 即 `static`、`0` 即 `dylib`，未设时按 libdir 实物（含 `lib*.a`/`.so`）推断（[build/main.rs 507-545](https://github.com/rust-openssl/rust-openssl/blob/openssl-v0.10.82/openssl-sys/build/main.rs#L507)）。所有环境变量均支持带 target 前缀形式（如 `AARCH64_UNKNOWN_LINUX_MUSL_OPENSSL_DIR`，[build/main.rs 42-46](https://github.com/rust-openssl/rust-openssl/blob/openssl-v0.10.82/openssl-sys/build/main.rs#L42)），双架构 CI 应优先用带前缀形式防误用宿主机 OpenSSL。
- `[建议·正确姿势]` 沿用现有 workflow 先自建固定 OpenSSL 3.6.1（校验 tarball SHA-256、`./Configure linux-x86_64 no-shared ... make install_sw`，见 `.github/workflows/crypto-poc.yml`），再在 Rust job 中设 `<TARGET>_OPENSSL_DIR=<prefix>`、`<TARGET>_OPENSSL_STATIC=1`、`OPENSSL_NO_VENDOR=1`（双保险）执行 `cargo build -p boreas-crypto --features openssl-backend --target <target>`；aarch64 侧 ./Configure 目标切 `linux-aarch64` 并用原生 aarch64 runner。构建后继续 `readelf -d` 拒绝 `libssl.so`/`libcrypto.so`，并实测握手，不以链接期无报错代替协商证据。
- `[事实·musl 与构建依赖注意]` 主计划发行形态是 Linux x86_64+aarch64 全静态/musl 目标；需要区分 **OpenSSL 静态（`no-shared` → `.a`）≠ 全静态 libc 二进制**，前者已由现有 workflow 的 NOTE 显式声明，后者还要 musl target 与最终 ELF 的 loader 检查。自建 OpenSSL 需要其构建系统依赖：现有 workflow 安装 `build-essential perl wget ca-certificates`（OpenSSL ./Configure 与构建依赖 Perl，workflow 依据）；`openssl-src` 路线（本文不建议）另需 C 工具链且在部分平台对汇编例程自动检测 `nasm`（[openssl-src README](https://github.com/alexcrichton/openssl-src-rs/blob/main/README.md)）。交叉编译还需 `--cross-compile-prefix` 与目标 sysroot 纪律；**aarch64 不得用 QEMU 一次成功代替本机 runner 握手**（Phase 0 门禁），且 GHASH 指令加速须查 `CLMUL`/`PMULL`，不得只看 AES 指令集（主计划 §4.2）。

## 3. `draft-ietf-tls-mldsa` 当前状态（datatracker 实测，2026-11-15）

- `[事实]` 文档为 Active Internet-Draft（tls WG），Stream/WG state `Submitted to IESG for Publication`，IESG state `RFC Ed Queue`，RFC Editor status `Awaiting First editor`；现行修订 -06（September 2026），`Intended status: Informational`，过期日 `Expires: 15 March 2027`。[IETF datatracker: draft-ietf-tls-mldsa](https://datatracker.ietf.org/doc/draft-ietf-tls-mldsa/)
- `[事实]` §3 `ML-DSA SignatureScheme Values` 将三值映射：`mldsa44(0x0904)→ML-DSA-44→id-ML-DSA-44`、`mldsa65(0x0905)→ML-DSA-65→id-ML-DSA-65`、`mldsa87(0x0906)→ML-DSA-87→id-ML-DSA-87`；并要求 CertificateVerify 按所引 FIPS 204 `ML-DSA.Sign/Verify` 计算与检验。IANA 表同记三代码点且 `Recommended=N`。[draft-ietf-tls-mldsa-06 文本](https://www.ietf.org/archive/id/draft-ietf-tls-mldsa-06.txt)
- `[事实]` 三个维护中 TLS 生态的当前源码（§2 的 GnuTLS aid `{9,5}`、wolfSSL `0x09/0x05`、rustls `SignatureScheme::ML_DSA_65`、BoringSSL/AWS-LC `0x0905`）均收敛于同一代码点，所以短期互操作以 -06 为共同基线在工程上有据；但主计划已明令“不得将其冒称为已发布正式 RFC”，RFC 编辑队列期最终文本仍可能编辑性变动，**草案风险只能靠 ADR 冻结（-06、0x0905、后端版本表）与 RFC 发布后复核回归来吸收**。

## 4. 推荐组合与 CI 落地步骤草案（均为草案、非已执行）

### 4.1 推荐组合

| 层 | 选型 | 理由（一手证据指向） |
|---|---|---|
| 主 TLS 协议/密码实现 | OpenSSL `openssl-3.6.1` 固定 tag + tarball SHA-256（沿用现 workflow），`no-shared`、最小 `openssl.cnf`（仅 default provider） | 2026-11-14 评估取证 tag 源码 + CI run 的同实现 mTLS 成功一次；修复面最小。 |
| Rust 集成层 | `openssl 0.10.82` + `openssl-sys 0.9.118`（现 Cargo 钉版），非 vendored、自建 OpenSSL 注入（§1.4） | §1.1/§1.2 API 全部命中；策略只在 `SslContextBuilder` 一次性下发，握手后把读数喂 `Policy::{validate_negotiated, validate_peer}`。 |
| 第二独立实现（互操作对端，不进产品） | 首选 GnuTLS 3.8.13 `--with-leancrypto`；并跑 Go go1.27.4 `crypto/tls` 小对端；wolfSSL v5.9.4-stable 作可选第三 | GnuTLS 血统与维护方独立性最干净（§2.1）；Go 引入异语言异栈对证书互读的交叉检出率最高、成本最低（§2.4）。 |
| Rust 备胎 | rustls 0.23.46 + aws-lc-rs 1.19.0，provider 收窄（kx=[X25519MLKEM768]、cipher=[两类]、sig=[mldsa65 面]） | 仅在 OpenSSL 静态/FFI 路出现架构性阻塞时启用 PoC-B；与主路径只能二选一作产品后端，不并行出厂。 |

### 4.2 CI 落地步骤草案（按序，每步失败即停，不许静默降级）

1. **冻结 ADR 已选项**：RFC 9846/10024/9881、draft-ietf-tls-mldsa-06（0x0905）、OpenSSL 3.6.1（tag+tarball 哈希）、rust-openssl 0.10.82/0.9.118、GnuTLS 3.8.13（leancrypto/Nettle 小版本）、Go 1.27.4，写明 RFC 发布后复核触发条件。任何一项变动先进新 ADR。
2. **自建 OpenSSL 双架构**：x86_64 job 沿用现 workflow；新增 aarch64 原生 runner job（`./Configure linux-aarch64 no-shared`），各产出 `<TARGET>_OPENSSL_DIR` 目录并 `readelf -d` 验 CLI 与后续 Rust 产物无 `libssl.so`/`libcrypto.so`。
3. **Rust 后端 build-only 冒烟**（实现阶段）：`<TARGET>_OPENSSL_STATIC=1` + `OPENSSL_NO_VENDOR=1` 构建 `cargo build -p boreas-crypto --features openssl-backend --target x86_64-unknown-linux-musl` 与 `aarch64-unknown-linux-musl`；断言 ELF 无 OpenSSL 动态依赖且二进制可在本机 runner 启动做 self-check（不冒称 TLS 可用）。
4. **同实现回归**：重跑 `run-openssl-mtls.sh` 全绿后，再让 Rust 后端示例二进制复刻同一组断言（两 AEAD、group `X25519MLKEM768`、`Signature type: mldsa65`、server/client CertificateVerify state、四负测），日志与证书样例经现有 sanitizer 出 artifact，不外泄私钥/PSK。
5. **独立互操作矩阵**（Gate 决定项）：{OpenSSL(Rust 后端) ⇄ GnuTLS} 与 {OpenSSL CLI ⇄ Go} 各跑双向（server/client 互换）× 两 AEAD × 同一份 ML-DSA-65 证书链；每方独立打印协商组/套件/sigalg 而不是共享日志；失败关闭复测：仅经典组、无客户端证书、AEAD 无交集、错 role/跨 net 证书（应用层断言）与过期客户端证书。
6. **协商读数改造前置**：互操作留证不能只靠对端日志，须优先补 negotiated group / peer sigalg 的可靠读数通道（§1.3），否则 `G-CRYPTO` 的“实测协商值”主张仍不成立。
7. **pq1024 不在本轮**：`SecP384r1MLKEM1024 + ML-DSA-87` 另立 profile 与独立互操作，`Suite::Pq1024` 继续默认关（`lib.rs` 现状正确）。

## 5. 最大风险与失效模式

> **最大风险**：`draft-ietf-tls-mldsa-06` 尚在 RFC Ed Queue（§3）——代码点虽有多实现收敛，IESG/RFC-Editor 最后文本变动、以及将来 RFC 与 -06 代码点/语义若分叉，将同时动摇 OpenSSL、GnuTLS、wolfSSL、Go、rustls 五个实现当前选用的 `0x0905` 前提；缓解只有 ADR 冻结 -06 + 发布日回归与可切换的后端版本表，**不许**以私有代码点或自写扩展绕开（违反主计划即判不合格）。

- **OpenSSL 3.6.1 证不了静态发行**：现有证据是 CLI `no-shared` 只验两个 OpenSSL `.so` 缺席；musl 全静态 + 双架构本机握手仍缺（主计划 §1.1），外加 negotiated-group FFI 缺口（§1.3）直接挡住“不得由 config 假设协商”的验收口径。
- **vendored 误点**：任何人在 feature 上叠加 `vendored` 会悄无声息换到 OpenSSL 3.2.0 历史行为——CI 须显式 `grep -r vendored Cargo.toml` 负断言且用 `OPENSSL_NO_VENDOR=1` 封死。
- **格式代际差**：ML-DSA 私钥 PEM/DER 于 lamps 草案 04→12 间有 seed/expandedKey/both 三语义并存史（GnuTLS NEWS）；OpenSSL 生成的密钥被另一实现拒读是跨实现互操作中最可能的前锋失败，须对三种格式各测一轮。
- **“同谱系冒充独立”**：BoringSSL↔AWS-LC↔Boring API 共享血统若被记作第二独立实现，会虚增 `G-CRYPTO` 交叉验证的可信度（§2.3）；rustls 作第二时也须如实标注其底座来源。

## 6. 未证实项与已查范围（如实清单）

- `[待证·交付时形态]` 他线 `backend.rs`（576 行）只读展出，本文未执行其编译或握手。三项须经实现评审/新 ADR 逐条处置（§1.3 已展开）：

  (2) `session_reused` 经 `unsafe { openssl_sys::SSL_session_reused(ssl.as_ptr()) }` 读，谓词之正确性系于 `as_ptr` 不转移所有权之约定而非安全层 getter；
