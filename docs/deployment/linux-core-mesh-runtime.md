# Dedicated Linux Core mesh runtime

`boreas node mesh-run /absolute/node.toml /absolute/material /absolute/runtime.toml` (Linux binary with `openssl-inner-tls`). This is separate from `daemon` and `mesh-probe`. A source opens the circuit; either endpoint can send IPv4 traffic once it is up. One instance serves a single permanent Core VIP pair over up to three preprovisioned paths (three or four distinct Cores per path). Source must be the lower Core slot. This does not enable general/Edge subnet routing, discovery, unrestricted LSA flooding, generic listener multiplexing, IPv6, DNS, DIR, or hitless migration.

## Supply trust and topology

Use a version-2 Core node configuration (`pq768`, `e2e-required`, no `[dns]`, all optional limits off). Provide its private `identity_key`, exactly one roots bundle, and durable `state_dir` for one service owner. `[uplink]` remains required by the standard configuration schema; mesh locators come only from the separate runtime manifest. Protect both configuration files with mode `0600`. Use absolute paths and trusted, non-symlink directory ancestors (a root-owned sticky ancestor such as `/tmp` is allowed); private keys must not be group/world-accessible. Run endpoints as an unprivileged dedicated service UID. Do not place root, status or delegated signing private keys in the runtime directories.

The normal `pki issue-node`, `pki sign-status`, and `pki sign-policy` flows supply the node credential, StatusSnapshot and network policy. Stage the independent NetworkRoot pins and network policy in `state_dir` under `network-root.ed25519.der`, `network-root.mldsa65.der`, `network-policy.tbs`, `network-policy.ed25519.sig`, `network-policy.mldsa65.sig`. The roots bundle must include the StatusSigner, IdentityAuthority, and a root-authorized CoreOperational signing grant scoped to each graph member. For each member, provision its dual-signed `NodeIdentity` and `CoreLsa`; these are not generated by the runtime. `CoreLsa` is signed by the member's scoped CoreOperational key, with monotone sequence and expiry, and contains the CDN-class neighbors on both sides of each authorized edge. Never reuse the test private keys or the test certificate authority in deployment. The Linux/OpenSSL CLI supports the following separated provisioning flow (example for Core 1):

```sh
# On the Core's provisioning host, NOT in the runtime material directory:
boreas pki core-request /secure/core-1 "$NET_ID" 1 1 30
# Offline NetworkRoot host: authenticate the operator/request out of band.
# Import only the public core.request, not the Core's key files.
boreas pki core-authorize /offline/ca /offline/roots.cbor /offline/core-1.request /offline/roots-1.cbor 1
# Repeat authorization for each distinct Core using the previous output as input.
# Send the final public roots bundle back to each signing host and runtime.
boreas pki core-sign-lsa /secure/core-1 /secure/final-roots.cbor /secure/core-1-lsa.new 1 1 120 2:5:0 3:30:0
```

The final command takes Core generation, sequence, TTL in seconds, then zero to fifteen `peer:rtt-ms:loss-ppm` tuples for CDN-class neighbors. An empty list withdraws all adjacency. Every signer re-verifies the result against the delegated public keys. Approval is one Core grant per slot; for rotation make a new bundle from the operator-approved base and coordinate a restart. Use versioned, new output filenames; operators handle monotone sequence storage and publish the new signed files via atomic rename, not by writing directly into a live mailbox.

Material filenames: `identity.pem`, `identity-ca.pem`, `local.signed`, `local-lsa.signed`, `status.signed`, plus `core-N.signed` for every `peers` slot and `core-N-lsa.signed` for each peer seeded locally. Relay/destination need `outer.pem` (leaf first then intermediates) and `outer.key`. Source/relay use platform Web PKI, or an explicit `outer-ca.pem` whose roots replace platform roots; TLS 1.3 and hostname verification stay enabled in either case. A name/IP locator never confers identity. Hop and E2E pq768 mTLS remain bound to the signed node SPKIs. A status snapshot cannot carry independent identity denials. Publish such a decision as `identity-revocation.signed` (existing IdentityAuthority mailbox format), not through StatusSigner; committed denials survive mailbox deletion and process restart.

Publish updates via atomic rename. Active attempts are capped at five seconds and are further constrained by policy/identity/LSA/status cutoffs. Status, identity revocation mailbox, and signed topology are reloaded before each admission/epoch and polled when idle; a mailbox arriving mid-attempt applies locally at the next authority boundary (at most three five-second attempts in one source selection). Without configured directory neighbors, `core-N-lsa.signed` files seed the process-local LSA directory and are required for a cold start. When an authenticated direct hop advertises a newer valid LSA for its own Core, the runtime retains the exact signed bytes, aborts the old route before business bytes, and rebuilds the graph at the next admission. A missing file or a still-valid, authenticated older seed may use the newer in-memory head; an invalid, expired or equivocating file is not silently ignored. An expired or poisoned head is never replaced by an older version. Use `(core_generation, seq)` for LSA versions, with nonregressing issuance times and operator-controlled generation changes.

### Optional cross-hop CoreLSA directory

With no `[[directory]]` entries, the seeded behavior above is unchanged. For cross-hop synchronization, provision an adjacent, dedicated directory socket for each intended control edge. The lower slot initiates and the higher slot listens; the authenticated peer identity comes from `core-N.signed`, not DNS or the advertised LSA. Example: Core 1 sets `[[directory]]` with `peer = 2`, `next = "192.0.2.2:18182"`, `tls_name = "core2.example.com"`. Core 2 sets `[[directory]]` with `peer = 1`, `listen = "192.0.2.2:18182"`, and a separate entry to dial Core 3; Core 3 listens for Core 2. Never reuse a business listener. Any directory listener needs the same outer server credentials; any directory dial uses the same verified outer TLS roots. All local and remote signed identity files and root grants remain mandatory. In this profile omit learned peers' `core-N-lsa.signed` files (optional bootstrap seeds); unknown heads delay opening TUN or business listeners. A seed supplied on disk remains an authority input and must not be left to expire.

Directory uses the same strict pq768 mutual authentication, probe, direct signed LSA exchange, and durable identity revocation exchange before accepting any third-party object. It reuses wire `DirectoryPage` unchanged: one original signed CoreLSA per page, a consecutive transaction-local ordinal (never an object sequence), at most 14 third-party heads plus a final page repeating the peer's exact direct advertisement. One connection per exchange, existing admission/byte credits and the same five-second maximum attempt including the directory phase. Every origin must be configured locally; forwarded signatures, writer scope, UTC validity, revocation, and replay are checked locally. A valid signed withdrawal (including an empty neighbor list) can cross a preprovisioned control edge; this never authorizes business across that edge. Same-version signed forks freeze the existing process-local replay slot. Already authenticated pages can be committed individually even if a later page or the exchange fails.

Outgoing anti-entropy is scheduled five seconds after the previous attempt on that neighbor and runs serially with other control work and bounded business epochs; this is not a five-second delivery SLA. This slice does not implement event-triggered push, discovery, Edge/identity/lease distribution, durable LSA replay or equivocation evidence, or in-place recovery once the runtime stops on expired, conflicting, or revoked authority. During partial convergence a downstream failure may still appear as pre-confirmation failure at the source; this does not authorize transport failover. A coordinated restart is required for local identity/policy/root rotation. Repair invalid authority before restarting; do not delete durable status state.

## Configure dedicated listeners and TUN

Example source (`peers = [2, 3, 4]`):

```toml
mode = "source"
peers = [2, 3, 4]
tun = "btun0"
mtu = 1400

[[routes]]
path = [1, 2, 3, 4]
next = "192.0.2.2:18082"
tls_name = "core2.example.com"

[[routes]]
path = [1, 3, 4]
next = "192.0.2.3:18083"
tls_name = "core3.example.com"
```

At Core 2 use `mode = "relay"`, `peers = [1, 3, 4]`, no `tun` or `mtu`, and only the primary path with `listen = "192.0.2.2:18082"`, `next = "192.0.2.3:18082"`, `tls_name = "core3.example.com"`. At Core 3 use `mode = "relay"`, `peers = [1, 2, 4]`, a listener for each path (`192.0.2.3:18082` and `:18083`) and corresponding distinct destinations (`192.0.2.4:18082` and `:18083`) under `core4.example.com`. At Core 4 use `mode = "destination"`, `peers = [1, 2, 3]`, the same TUN settings as the source, and both paths with `listen` only. Start destination and downstream relays before source. Every path is explicitly authorized at every participant.

An administrator must provision one persistent `IFF_TUN|IFF_NO_PI` queue belonging to the unprivileged service UID at each endpoint, bring it up, match the MTU and configure the two /32 routes. For example, at Core 1:

```sh
ip tuntap add dev btun0 mode tun user boreas
ip link set dev btun0 mtu 1400 up
ip addr add 10.20.1.1/32 dev btun0
ip route replace 10.20.4.1/32 dev btun0 src 10.20.1.1
```

At Core 4 exchange the addresses. Do not point an underlay IP or a default route into TUN; relays have no TUN. The runtime only attaches and verifies the existing queue; endpoint packets must match the two authenticated permanent IPv4 VIPs regardless of system routes. Start the command under a service manager that captures stderr and terminates it via SIGTERM; the dedicated runtime does not start a control socket.

First selection ranks eligible signed paths. After a confirmed transport loss it tears down the old circuit and tries a remaining signed path with fresh hop and E2E TLS, keeping the last confirmed first hop preferred across normal short epochs. Failover never copies packets already dequeued for the failed path or old ciphertext/TLS records. Ordinary TCP recovery or a fresh independent packet belongs to the caller. Auth/protocol errors (including a reset or EOF before confirmation), expiry and revocation are not retryable path-loss evidence. Saturation can drop packets; the design has one owner/active circuit per process, at most two admitted links at a relay, and fixed packet/frame buffers. Logs report circuit IDs and packet/ciphertext counts, not packet contents.

## Acceptance

Existing signed graph + genuine TLS coverage: `cargo test --locked -p boreas-tunnel --features openssl-inner-tls --test mesh_probe_live`.

In a controlled Linux runner with reviewed OpenSSL (the same backend as `rust-tls.yml`), build the acceptance target as a regular test invocation, then run its binary as root in the disposable runner. The test requires CAP_NET_ADMIN/CAP_SYS_ADMIN, `/dev/net/tun`, `ip`, `ping`, `unshare`, `mount`, and `setpriv`. It creates four network namespaces, starts four actual unprivileged Boreas subprocesses, attaches two real persistent TUNs, pings in both directions across distinct confirmed circuits, kills the active first relay, confirms the backup circuit has a fresh ID at both endpoints, inspects packet/ciphertext counters, then publishes an independently signed Core revocation and requires source to exit with status 2. No real CDN or external address is used.

```sh
cargo test --locked -p boreas-cli --features openssl-inner-tls --test mesh_run_netns --no-run
# Use the exact executable path printed by Cargo:
sudo --preserve-env=OPENSSL_CONF /path/printed/mesh_run_netns-HASH --ignored --nocapture --test-threads=1
```

A normal unprivileged test run leaves this integration test ignored. Only output from the explicit privileged invocation is real TUN/process acceptance evidence.
