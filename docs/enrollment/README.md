# Durable Enrollment transaction module (draft)

This document describes the exported `boreas_pki::enrollment` policy module. It is not an online enrollment service and is not production-ready. The OpenSSL/CSR verification and IdentityAuthority signing layers are intentionally future integration work.

## API and trust boundary

The state machine accepts `VerifiedEnrollmentRequest`, whose fields and production constructor are private to this crate. A future CSR module may construct it only after verifying exact raw DER proof-of-possession and computing SHA-256 over those exact bytes. It carries both the bounded raw CSR DER (up to 16 KiB) and its digest; PREPARED journals the bytes, and `raw_csr_for_signing` retrieves those identical bytes after recovery so a retry cannot silently re-encode/re-sign a changed CSR. There is no `bool` validation argument or unchecked public constructor. Unit tests have a test-only bypass. `SignedIdentityResult` similarly has no production public constructor in this draft; future IdentityAuthority integration must create it from the exact signature result (up to 16 KiB). This module does not parse CSR, verify proof-of-possession, create signatures, or authenticate an invite itself. The request contains the bearer secret and store compares it to an invitation's 256-bit secret without a boolean assertion; secret provisioning/transport remain future integration.

`EnrollmentStore::claim` performs a durable PREPARED transition: one invite is bound to `(enrollment_id, raw_csr_sha256, exact raw CSR bytes)`, one address slot within that invite's exact role and permanent `home_core_id` scope is reserved, and that NodeID's next identity generation is allocated. Invitation authentication checks a 256-bit bearer secret plus role/home-core scope and expiration. A repeat of exactly the same tuple returns the same persisted transaction state. Different CSR bytes or enrollment ID cannot reuse the invite. `mark_issued` durably stores the signed identity result; retry with identical result bytes returns the existing result, while a different result is rejected. `mark_delivered` persists acknowledgement. A bound request can retrieve the same result only through the invite expiration plus the bounded 24-hour recovery window.

The `WriterFence` is an opaque crate-internal value expected to come from a future external, durable fencing authority. The module compares a provided epoch with the journal's highest observed epoch and persists a Fence event on open, but does **not** implement cross-host consensus, fencing lease issuance, or protection against a second machine with an equivalent/newer token. A fence epoch is useful only when the integration ensures the external authority never reissues a stale epoch. The create-new sidecar lock prevents ordinary concurrent opens on one filesystem. If a process crashes, its lock file remains; after fencing the old writer, an operator must inspect the process and journal, then remove the stale `.writer-lock` file to resume. On normal store drop, the module closes and removes the sentinel. Initialization failures after this process created the sentinel also remove it; crash remnants are never removed automatically. Never automatically delete/steal a lock based on PID or age.

## Journal and recovery

Events are append-only frames: `BENR`, version byte, big-endian payload length, CRC32, and deterministic internal payload. A `Fence` event is synchronously appended during `open` before the handle is returned, so a later restart compares against the last durably recorded epoch even if no enrollment claim occurred. Every state transition writes one complete frame and calls `sync_all()` before updating in-memory state. Input bounds currently include 16 KiB for CSR digest-associated raw DER and signed result (the module receives only the digest plus length after future validation). A write or sync error poisons the live store so it will not claim success on that instance. On reopen, a truncated final header or payload is ignored and the file is truncated to the last complete frame followed by `sync_all`; complete bad magic/version/CRC or invalid transition is rejected rather than silently repaired. This makes a missing/incomplete final append mean “not committed”; a full valid frame means “committed.”

CRC32 detects accidental corruption and torn-write damage only. It is **not** an authenticator and does not prevent malicious modification, rollback, or replacement of the journal. Protect storage with OS permissions, backup/restore fencing, and a future authenticated integrity mechanism as appropriate. Input invite/slot configuration is supplied again at open and must match the provisioned authority data; the journal validates persisted NodeID/slot and invite references against that supplied configuration.

## Bounds and allocation behavior

Current policy caps: CSR DER at 16 KiB, signed result at 16 KiB, invite count at 100,000, provisioned slots at 4,016, journal at 64 MiB, and committed transaction count at 16,384. These are implementation safety bounds, not system capacity claims. The journal is not compacted; reaching bounds fails closed with `StoreFull`. Slots are quarantined after use in this initial module. `tombstone_slot` durably advances a generation, but safe slot reuse is intentionally not implemented until address reclamation, all lease/snapshot TTL expiry, and persistent generation fencing are integrated.

## Failure tests included

Tests in the module cover PREPARED → ISSUED → DELIVERED reopen/retry, exact idempotency, competing CSR requests, 16 serialized racing requests, recovery-window expiry, torn final tails, complete CRC damage, lock collision, stale fencing epoch, and durable tombstone generation. A direct failing-filesystem/fsync fault injection backend is not yet included; the normal I/O error path is implemented to poison the store, but disk-failure injection and crash-point matrix remain an explicit follow-up. The 16-thread tests exercise one shared process-local mutex/store and do not establish 16-process or distributed race safety.

## Remaining integration and security boundary

Before production use: implement CSR DER parsing and real proof-of-possession verification (OpenSSL path); compute SHA-256 from the exact persisted CSR bytes, not caller-provided digest; provide typed invite authorization; make the IdentityAuthority signature result verifiable and transactionally retrievable; supply a durable writer-fencing service; test crash injection at every append/fsync boundary, disk-full and sync failures; harden journal directory permissions/symlink handling; define backup rollback detection; and add multi-process/multi-host tests. This draft must not be described as a completed EnrollmentService or as passing any G-CRYPTO gate.
